From a book to a grounded answer.

The project has two flows: explicit PDF indexing, and the Streamlit question flow. Each question retrieves up to three book chunks, formats page-labeled context and sources, then passes the question, context, and chat history to the answer model.

Separate inputs: Streamlit sends the current question to retrieval and generation. st.session_state.chat_history goes to generation only; it does not feed query embedding or Chroma search. A follow-up like “How does it work?” may therefore retrieve weak evidence even though Llama sees the earlier conversation.
Source display branch: format_context() sends page-labeled text to the prompt, while format_sources() sends page, distance, and snippet details directly to the Streamlit source expander.

Two models, two jobs

embeddinggemma converts text into vectors for search. llama3.2 writes the answer from the prompt and evidence. Changing the embedding model requires rebuilding a compatible index; changing the answer model does not itself require re-embedding the book.

Three forms of memory

Chroma: persists book chunks on disk across app restarts.
Chat history: lives in the Streamlit session and feeds generation.
UI messages: replay the chat display; retrieved source lists are not saved with those messages.

Chunk size is measured in characters

Your splitter uses Python string slices, not token counts or sentences. Overlap reduces boundary loss, but words and explanations can still be split. At most roughly 3,000 chunk characters enter each answer's retrieved context, plus labels and separators.

Index reuse has a limitation

The notebook skips embedding when stored record count equals expected chunk count. That checks quantity, but cannot prove that the PDF, chunk settings, or embedding model are unchanged. Index freshness would need additional checks.

Evaluation is a separate workflow

evals/evaluation_dataset.json preserves the 20 questions and their page-level labels from Evaluation/MMDS_RAG_evaluation_dataset_20.csv. evaluation.py runs dense retrieval metrics, generates answers from the retrieved chunks, and writes per-question JSON/CSV files plus an experiment summary in experiments/results.csv. The JSON includes full retrieved chunk text, expected and generated answers, and token usage. Retrieval scores are page-level proxy metrics, not chunk-level judgments. A separate basic LLM-as-a-Judge review of the 20 answers is recorded in experiments/retrieval_runs/LLM_as_a_Judge_LargeDocRAG_Results.xlsx; judge scoring is not automated by the runner. The workbook reports averages of 4.25 correctness, 4.55 groundedness, 5.00 relevance, 4.25 completeness, and 4.51 overall. The judge model, prompt, and detailed rubric are not recorded, so the results are an initial review rather than a fully reproducible judge evaluation.
